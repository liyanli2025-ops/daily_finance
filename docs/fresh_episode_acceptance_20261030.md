# 下一次真实验收使用新一期资料

用户要求：下一轮口播真实验证前完整采集新新闻，检验修改是否能迁移到新事件，停止反复围绕10月29日人工样稿验证。单期新样本通过仍不能证明普适性或预测胜率。

## 本次实现

`app.radar_check`在采集前读取当前App名单，记录采集开始/完成时间及名单签名；完成前再次核对，名单改变则停止写入本次新闻验收快照，不把混合名单标成可用。内部公开缓存可能已写入，不能宣称整个采集事务回滚。

新增`app.fresh_input_check`：只读App名单和本地快照，校验完整采集、两小时内起止时间、技术采集时间、名单、重选指纹及正文记录；分别统计入选文章24小时、72小时、旧背景、未知及未来发布时间。不会因本次抓取而把旧文标为新消息，也不强制每只股票有新闻。

这是独立免费准备检查，不替代生产质量门禁，不授权付费。技术采集时间新不代表K线交易日新，需结合休市及各市场实际数据截止日人工核对。全文标记不等于逐字核实，来源失败/研究缓存是否过期仍要看对应诊断。

## 下一轮执行顺序（代码部署后）

1. 保持automation_paused=true；把当前口播规则及本次采集检查一起合并安装，不为本次小改立即发一个独立补丁。
2. 服务器手动执行一次公开资料采集，读取当前App自选股，覆盖公司、行业、全市场、海外及技术行情。继续遵守既有失效来源暂停策略。新公告/财报/研究资料按实际可用性采集；历史基线可复用但保留日期，不清空历史证据强迫重复下载。
3. 完成后运行选材及新资料免费检查，并检查源失败、原文范围、当期行情截止、缓存有效期、关键证据与输入费用预算。收集失败停止，不能把上次成功快照冒充本次结果。没有重要公司新闻不阻塞其他有价值选题。
4. 冻结本轮快照、阅读范围及输入指纹。生成报告必须来自新资料且走正式分析路径，不人工挑三条旧新闻或手写答案。费用预览明确各阶段次数；不使用旧的四请求命令直接盲跑，不自动修稿重试。
5. 分析结果先核对事实、论证与实际用途；通过后以该报告生成口播。若人工改稿，保留改前改后及原因，只能算辅助编辑成功，不能称全自动流程通过。
6. 口播核对主线、听感、数字负荷、条件和实用判断，通过才做音频。调度继续暂停。其后用不同市场状态的数期记录考察稳定性，不追求一次试验宣布完成。

```bash

sudo ./venv/bin/python -u -m app.radar_check --hours 72 --full-news
sudo ./venv/bin/python -u -m app.selection_check
sudo ./venv/bin/python -u -m app.fresh_input_check

```

上面列出顺序，不是已经执行的服务器结果。长采集应在nohup或终端会话中保存日志；没有采集成功与当前快照核对结果，不开始模型验收。这些模块不生成报告/音频，不恢复调度。付费命令将在新资料和预算明确后单独提供。
