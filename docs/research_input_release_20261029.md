# v10：补查与研究底稿输入合并修复

## 为什么做

v9实际口播已经执行且未通过人工质量审阅，旧人工修正版的收费试稿结束。本轮回到研究输入：上一轮修复了全池search_materials最早命中附近硬截800字符；本轮修复ResearchHub初始研究底稿body[:limit]，不宣称改变口播模板就能解决分析深度。

## 研究底稿的改动

- financial_baseline中有明确标签的指标行按完整行提供，保持期间、币种、字段名、数值与单位，不截半个数字。旧的叙述型财务背景仍可按完整句读取，不强行当成指标表。
- 长研究叙述复用已有完整句/经营陈述与限定选句，保留来源主体和日期；选中后段时补上对应原PDF页码或镜像分片，分片不能改叫PDF页码。仅词项/位置辅助，不是语义理解或财务结论。
- 完整URL及缓存组装时点仍保留在Material和当期证据库；初始提示词使用较紧凑的来源元数据，保留来源、发布日期、统计期、读取状态和[N:ID]，减少重复长URL挤占正文。read_material仍可取得完整元数据。
- 按最终渲染文本计算预算，正文范围标签也计入；默认研究初始总预算仍8000字符、旧背景预算仍受限，没有放大资料池或付费请求预算。
- prompt_reading记录每份材料实际提供的原文范围/字符数；时效排除、未来材料、预算不足、超长完整单元未提供均有明确状态。准备过不等于模型读过，读过存储节选不等于读完原报告。
- 没有按当前自选股硬编码规则，四只动态股票共享8000字符的测试保留少量完整财务背景，不将它们当今天催化。长表格的列关系仍未自动理解，不能据文本位置配对数值。

## 免费核对入口

app.research_input_check只读取App当前名单和有效研究缓存，使用正式ResearchHub.prompt的8000字符分配。打印缓存份数、实际准备份数、原文字符数、材料类型和未提供原因。--details可显示范围及最多12段180字符预览；这只是终端预览截短，不是再截短入模正文。

不调用collect/get_json、LLM或TTS，不写App、不解除暂停。缓存若已过期会如实显示缺失，不自动补采。用户原归档没有独立ResearchHub缓存，本轮不能声称服务器研究材料真实覆盖已验收。

## 安装与检查

上传finance-research-input-20261029-v10.zip到腾讯云/tmp。先按交付消息校验SHA，再执行：

```bash
python3 -m zipfile -e /tmp/finance-research-input-20261029-v10.zip /tmp/finance-research-input-upload-v10 &&
sudo /var/www/finance-daily/backend/venv/bin/python /tmp/finance-research-input-upload-v10/finance-research-input-20261029-v10/install_upgrade.py --apply --restart &&
cd /var/www/finance-daily/backend &&
sudo ./venv/bin/python -u -m app.research_input_check
```

安装器校验精确已知源文件、私有备份，保留.env、数据库、前端静态目录、暂停及其他项目。新增用户已确认v9基线，来自原部署包及Git源文件的固定指纹；未知差异停下，不绕过manifest。不能运行旧programme试验来“验证v10”，它已经结束且输入固定，不能验证新研究层。

检查目标不是凑份数。若缓存有资料但正文准备为0，要看时效、预算或正文格式；若缓存缺失/过期，不宣称全网没资料。默认输出较短，足以决定下一步具体检查哪份原文，不必先触发新收费生成。
