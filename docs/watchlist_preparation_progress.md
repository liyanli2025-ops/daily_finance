# 新增自选股后的资料准备

2026-10-28。本轮代码及本地模拟验收完成，尚未部署。没有真实行情/新闻请求、模型调用或TTS；线上持久暂停仍保留。

## 用户可见行为

正常运行时，添加股票先提交App名单，再把该条记录加入后台补采队列，前端显示正在准备的阶段。准备使用当前数据库名单、历史日线、业务/公告/研究资料及近72小时定向公开媒体资料，不要求这只股票事先存在于本地历史库。

新股缺少60期日线、公司业务资料未取得、没有取得公司专属新闻或部分研究接口失败，结果是partial，卡片说明实际缺口。没有取得不等于不存在。本次补采完成不代表资料足够支撑判断，也不证明新闻有投资价值。用户可手动点击补采；15分钟内复用本次结果，不因重复点击重跑。

维护标记data/.automation-paused存在时，只保存名单并显示暂停，不入队、不触发资料请求或模型。暂停后也不会由查看页面自动补采。补采中若遇维护暂停或该记录已删除，后续阶段停止；已经发出的公开请求可能完成，不能声称可以撤销在途请求。移除后重新加入同代码会有新的记录ID，不复用旧任务的身份。

## 实际接入

- 新增POST /api/stocks/watchlist后登记BackgroundTasks，不改变添加接口原有Stock响应结构，只增添可选preparation字段；App主数据库无新增列、表或迁移。
- GET /api/stocks/watchlist/preparation只读状态，不抓行情、不补采、不调用模型。股票页有进行中任务且处于导航焦点时，用该接口串行轮询，最多30次；离开页面取消定时器，失败停止。不用含报价的整个自选股GET做轮询。
- POST /api/stocks/watchlist/{id}/prepare仅对仍在名单里的记录重试资料准备，仍遵守维护暂停及冷却；不生成报告、音频或交易建议。
- 准备先利用TechnicalRadar当前名单补历史行情，再用ResearchHub采该公司的公开资料，最后用已有MediaCollector的公开定向检索补新闻，原文进入现有短期NewsArchive。没有声称覆盖全部媒体或外部付费研报库。
- 状态文件在data/radar/watchlist-preparation，只保存身份、阶段、计数及覆盖结果，不放原文正文。状态24小时到期，由既有清理入口触发，暂停期间不会凭空定时清理；2小时后不标为当前有效。原文和研究缓存使用原有生命周期。OS锁是无正文的协调文件，不随状态清理，防止删除仍被使用的锁造成并发重复。
- 同一条记录由排他OS锁和任务令牌去重，服务内并发为1；不同进程也不能同时执行同一任务。任务有180秒总等待上限。进程中断会释放OS锁，记录可由明确的补采请求恢复；本版本不在服务重启或GET时擅自恢复所有任务。失败不自动无限重试。

## 生成期间名单变化

早晚报采集前记录市场/代码/名称签名，进入分析前核对；分析再绑定自己的名单。模型调用前、网关每次HTTP尝试前（包括内部重试），以及回复后、报告生成结束时再次检查。

若名单变化或数据库读取失败，停止本期后续生成，不把旧资料当成新名单的分析。完整模型回复已经取得时，会在generation-watchlist_changed_response检查点保留，再停止，不因名单变化自动重跑扣费。此机制覆盖正常早晚报的采集→分析窗口；独立脚本没有传入采集签名时，仍需它自己的快照/名单前置核验，不能认为任意外部输入都已自动匹配当前名单。

检查后至数据库写入之间不是跨请求的数据库锁；本轮没有引入全程锁表或修改App数据库。报告代表其生成快照，不会因为随后又改名单就自动变成新报告。
